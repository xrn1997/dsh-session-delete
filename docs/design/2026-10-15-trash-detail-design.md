### 1.1 多帧 zstd——本轮最硬的一条事实，AGENTS.md 已同步更正

- **Node 的 zstd 只给第一帧**：`zlib.zstdDecompressSync(buf)` 与 `zlib.createZstdDecompress()` 流式**都**停在第一帧（那个 3.8 MB 的文件两个 API 都只回 209 字节，流式那次还抛 `The operation was aborted`）。会话日志是一次次 append 出来的**帧序列**，所以要自己走帧。
- **帧结构（36 904 帧的逐帧读数，不是推断）**：`descriptor` 恒为 `0x04`（bit2 单段 ⇒ 无 Window_Descriptor，FCS flag=0 ⇒ 1 字节，DID flag=0 ⇒ 无字典）；帧体按 3 字节块头走到 `Last_Block`（type 0 Raw / 2 Compressed 是 `size` 字节跟着，type 1 RLE 跟 1 字节）；**帧尾恒多 4 字节**——注意 `descriptor` 的 bit5（Content_Checksum_flag）**从没置位**，却每帧都带这 4 字节，所以**不能按规范那一位决定读不读，得按实测**。
- **读法**：`magic(4) + desc(1) + [Window 1B 若 !single] + [DID] + [FCS] + 若干块(3B 头 + 体) + 尾 4B`；那 4 字节用「跳过它之后必须正好撞上 magic 或到 EOF」来确认。
- **自证**：这个解析器与"扫 magic 找边界"在 125 个文件 / 36 904 帧上**逐帧完全一致**，且每一片 `zstdDecompressSync` 都解得开（失败 0）。写差分测试时把这组事实钉住：单帧 / 多帧 / 三种块类型（Raw·Compressed·RLE）/ Reserved 那块抛 / 带尾 / 尾残缺。
- **形态分布（同一趟量出来的，不是假设）**：块类型只有 `Compressed` 36 630 与 `Raw` 620（**没有** RLE，Reserved 那位也没有；但 Raw 那条路在生产上真跑，所以块体长度必须算进去——早先按规范把 Raw 当"0 字节跟随"就会整段算歪）；每帧 **1～120 块**（绝大多数 1 块，最长 120 块）⇒ 多块循环不是纸面分支。
- **一条护栏是必需的**：块界一旦算歪，块循环会**空转不停**（写用例时真卡死过一次：一个高重复内容的夹具被 Node 压成 descriptor `0xa0` 的另一种帧形态，解析器按字段表走偏之后整个测试进程挂死）。机制按 2026-10-15 复核批更正：**不是** `cursor += NaN`——`readUint24LE` 用 `|` 读，越界那三字节是 `undefined` ⇒ 恒回 **0**，而 0 的 `Last_Block` 位没置位，所以少了护栏每圈只 `cursor += 3` 却永不 break。现在的行为是"块头越界即抛"，**读不懂的形态会响亮失败**，不会静默切错帧——这也是为什么 `detail` 把解压失败折成 `io` 而不是回半截正文。
- 为什么不用「扫 magic」当生产实现：压缩体里出现 `28 B5 2F FD` 四字节是可能事件，扫出来的边界会静默切错帧；规范解析器错了会当场抛，且已被上面的逐帧一致性验过。

### 1.4 同一目录**可以并存多代日志**（2026-10-16 实测；纠正 §1.1 之后各处「一个目录一份日志」的隐含前提）

- **形态**：扫 `~/.dsh/sessions` 549 个目录 + `~/.dsh/session-trash`，**7 个目录各含两份** `*.jsonl.zstd`（1 个还在原处、6 个已在我们回收站里），全是 `session.v3.jsonl.zstd` + `session.v4.jsonl.zstd`。成因是宿主换代：`@deepseek-ai/dsh-session-format@0.2.0-rc.2` 的 `SESSION_FORMAT_VERSION = 4`，而老代**留在原地当历史语料**（其 `listGenerations()` / `historicalCorpusRevision()` 就是为此存在）。
- **读法上的关键事实：新代是老代迁移后的超集，不是增量**。对质（同目录两代逐帧解完）：`firstTs` 逐字相同（1790145141187）、开头那条提问逐字相同（`seq 9`「/improve-codebase-architec…」），而 v3 = 2254 条 / 40 条提问 / 末尾 9-23，v4 = 2497 条 / 47 条提问 / 末尾 9-30。另一条小会话两代都是 6 条、时间戳完全一致（纯迁移副本）。
- **⇒ 判据只有两条，且都不是口味**：① **取版本号最大的一代**；② **绝不把几代拼起来**——拼接会把老代那 2254 条重复计一遍，页面上会出现「计数比正文多出一截」那种对不上账的话。读到旧代的症状是**静默少一段**：上面那条会少 7 条提问、243 条记录，页面上看不出任何异常。
- **词法照宿主逐字**（`CANONICAL_LOG_FILENAME` = `/^session(?:\.v([1-9][0-9]*))?\.jsonl$/u`，我们只在剥掉它之后补 `.zstd`）：裸名 `session.jsonl.zstd` 是**第 0 代**（`sessionFormatLogFilename(0)` 就是不带 `vN` 的那支），所以「裸名 + v4」读 v4；`.v0`、前导零（`v03`）、大写、`.tmp` 一律**非规范名、不当会话日志**（宿主注释点名的正是这几类）。版本号按**数值**比，不按字符串（`v10` 胜 `v9`）。
- **旧写法错在哪**：`src/trash/detail.ts` 是 `listFiles(dir).sort()` 再取**第一个**后缀命中，`src/trash/reconcile.ts` 是直接取 `listFiles` 第一个命中。前者被 `.sort()` 钉死成**字母序最小 = 最旧那代**（`session.v3…` < `session.v4…`），后者跟着 readdir 序走（NTFS 按名字排序，实测同样是 v3 在前）⇒ 那 7 个目录里 6 个的详情与对账一直在读旧代。
- **落点**：判定收进 `src/log/session-log.ts` 的 `pickSessionLog(names)`（一处家；`SESSION_LOG_SUFFIX` 随之下线，现在唯一的词法就是那条正则），两个调用方各自只留一行调用。用例：`tests/session-log.test.ts` 五例（最大代 / 裸名算 0 / 数值比 / 非规范名 / 明文不算）+ `tests/trash-detail.test.ts`、`tests/reconcile.test.ts` 各一例按真实两代形态断言读到的是 v4。**明文 `session.jsonl`（宿主 `compression` 关掉那档）仍然不在读法内**——本插件的解码逐帧走 zstd，明文要另一条解码路，没证据就不开。
- **真机读数（一次性探针，跑完即删）**：这 7 个目录改后全部选中 `session.v4.jsonl.zstd`，逐帧解完 `unparsedLines = 0`、帧数 2–135，无一处抛。

## 2. 界面（落地后取代 §7 的状态④，并新增状态⑥）

### 2.1 两档形态与断点

- 面板根元素上挂 `ResizeObserver`，观测**面板自己那一块的宽度**（不是 `window.innerWidth`：宿主侧栏折叠/展开、拖动分栏都会改中央列宽）。`ui/Tooltip.tsx` 已经在用 RO，jsdom 的替身已在 `tests/client/support/setup.ts`（替身不产 `borderBoxSize` ⇒ 测试里由**显式喂宽度**驱动断点，不依赖 RO）。
- **［已回退，见 §6］****≥760px**：左右两栏。左清单 **316px 定宽**（含 10px 右内边距给滚动条），中间一根 `border-l2` 分隔，右详情吃余下、**正文自己限宽 860 且左对齐**（超宽屏不把文字拉成长线；这是原来 `COLUMN_MAX_WIDTH=760` 那条关心得换成"只限正文"的理由）。
  - 算术要摆明（页内边距沿用现状 `24px` 左右）：中央列 760 时详情净宽 ≈ `760 − 48 − 316 − 1 − 2×16` ≈ **363px**；900 时 ≈ 503px；1 200 时正文按 860 收口。⇒ **760 是"能读但不宽裕"的下限**，不是舒适宽度。中央列归宿主，真机常用在 900+；若真机读数觉得挤，**把阈值上调到 900 是一行的事**（记在这里当已知取舍，不当秘密）。
- **［已回退，见 §6］****<760px**：下钻。清单铺满；点行 → 详情铺满，左上给「← 返回清单」；Esc 返回。窄档没有同屏两栏（2026-10-01 真机在 520px 窗量过：中央列只有 405px）。
- 两档共用同一份清单与详情组件，差别只在容器与「是否显示返回」。

### 2.2 清单（左栏）

沿用现状的一切：按项目分组的卡片、组内与组间按删除时间倒序、`relativeTime` 分桶、组头从 `projectKey` 反推目录名、空态/读数中/读数失败三块。**（当时）唯一改动：行里的「恢复」「彻底删除…」两颗按钮退出——2026-10-15 真机反馈后已回退，见 §6**。

- 行 = 标题（一行省略）+「删除于 X前 · 大小」，整行是一个 `role="option"` 的可聚焦项。
- 选中态 = §1.3 那对 token；未选中行仍是 `bg-layer-2` + `border-l4`。

### 2.3 详情（右栏 / 下钻整屏）——四态

1. **未选中**：一句引导（「选中一条会话看它讲了什么」）。**宽档首读完成后自动选中清单第一条**（右栏空着比多一次点击更怪），窄档不自动下钻。清单为空或读数失败时右栏不出现（没东西可选，也没有动作可点——失败那块的「重试」负责把清单读回来）。
2. **读数中**：标题行 + 骨架若干行 + 一句「正在读这条会话…」。文案不带百分比（我们只有"一条 135ms"这种量级，给进度是假话）。
3. **读数失败**：`role="status"` 那块，原文上屏 + 「重试」——**与清单读失败同一口径**，且只影响详情块，清单照常可操作。**读数中与读数失败都不冻结「恢复 / 彻底删除」**：这两个动作操作的是清单里那条记录，不依赖详情读成功——否则一条读不出正文的会话就再也删不掉了。
4. **有内容**：
   - **标题行**：清册标题优先（保证「行里叫 A、点开也叫 A」）；清册标题为空串才回落到日志内 `session/title`。（原文写「右侧是「恢复」「彻底删除…」」，动作已回退到清单行，见 §6。）
   - **元信息三组**：① 时间——创建 → 最后活动（跨 X 小时/天）、删除于（绝对 + 相对）；② 体量——大小、轮数、真实提问数、助手回复数、工具调用数、模型；③ 位置——**完整 `cwd`**（日志 header 是无损原串，比 `projectKey` 反推强）、会话 id、回收站目录名、原本归档态。
   - **正文**：人与助手的文字按时间顺序成列。原判据是"纯文本 `white-space: pre-wrap`"（§1.2 的过滤口径不变），**2026-10-15 真机反馈后改成：助手侧渲 Markdown、用户侧仍是原话**；行的皮肤抄宿主 `MessageItem.module.css` / `AssistantMarkdown.module.css`（只有用户有气泡，助手不铺底）。裁定、来源与逐字读数见 §6。
   - **截断口径（必须写明，不是"大概能显示"）**：**每条文字截 3 000 字符**并加省略号（`truncated: true`）；**`messages` 累计上限 50 万字符**（CJK 最坏 ≈ 1.5 MB UTF-8），先到先止，余下的条数进 `omittedByPayloadCap`，末尾给一句「还有 N 条未显示」。这两个闸按 §1 的读数在本机**一条都触发不了**（最大那条正文 806 KB UTF-8 ≈ 27 万字符，最多 442 条消息）⇒ 它们是防异常膨胀的载荷闸，**不是读盘阈值**：不设"文件太大就拒绝"，实测最大单文件 4.66 MB、单帧明文最大 8.99 MB，逐帧解压的峰值就在这一档，加读盘闸只会把能读的正文挡在外面。

### 2.4 键盘

左清单 `role="listbox"`（单选），行 `role="option"` + `aria-selected`；↑/↓ 在清单内移动选中（到边界回环），Enter/Space 确认（宽档只刷新详情，窄档进下钻），下钻下 Esc 返回。roving tabindex：选中行 `0`，其余 `-1`。详情块**不加 `aria-live`**——读数中到读完是整块替换，加了会把整篇正文念一遍；只有失败那块保留 `role="status"`。

### 2.5 危险层级不变量（一条都没让）

整页仍然只有页脚「清空回收站…」一块实心红；「彻底删除…」在详情里仍是安静的红（只写 `color: --dsw-alias-state-error-primary`、**不写 background**，理由见 §7 现有那条：内联底会打死 `.ghost:hover`）；单条与清空的二次确认框共用同一组件、都用页脚那款实心红。**「恢复」保持描边**，不与危险动作抢层级。

## 3. 取数：第五个端点

```
POST /dsh-session-delete-api/detail      体 { entryId }   → RemoteResult<TrashDetail>
```

```ts
interface TrashDetail {
  entryId: string
  cwd: string; createdAt: number; lastActivity: number
  turnCount: number; userMessageCount: number; assistantMessageCount: number
  toolCallCount: number; injectedCount: number
  models: string[]; logTitle: string
  messages: Array<{ role: 'user' | 'assistant'; time: number; text: string; truncated: boolean }>
  omittedByPayloadCap: number
}
```

- **`detail` 不回灌清册已有的字段**（`deletedAt` / `sizeBytes` / `workspaceId` / `wasArchived` / 清册 `title`）：客户端按 `entryId` 与自己手上那份清单配对着显示。这样"清单里写的大小"和"详情里显示的大小"永远是同一个数，不会因两次读数不同而各说各话；`entryId` 之外的寻址字段（`projectDir` 等）也不上线。
- **`injectedCount` 必须上线**：正文里"为什么少了这么多条"要能与页面上的数字对账，不能沉默——与 §7 页脚那句「清空后不可恢复」必须看得见是同一条规矩。

| 改造前的链（`COLUMN → SCROLLER → 空态块`） | **(-5, -5)** = 居中（这对 -5 是面板内边距与清单列 10px 滚动条右内边距的既有让位——改造前就是这个读数，不是新偏差） |

## 9. 清单对账：回收站目录是唯一需要手动动的地方（2026-10-16 第七批）

**来由（用户的两个实验）**：把 `~/.dsh/storages/xrn1997_session_delete_trash/` 改名搬走 → 点刷新，面板内容不变；重启宿主才消失。改回来 → 刷新依旧不出现；重启才回来。追问「那这个刷新有什么意义呢」。**机制真相**：清单读的是宿主 storage 域，而域是**懒开且只开一次**（`src/index.ts`）：打开时把记录装进内存，之后读全是内存快照（`dsh-storage-domain` 源码逐行核过：`entries()` 就是 `[...records.entries()]`，`put/delete` 先落盘再改内存），宿主也没有文件监视 ⇒ 外面改 `storages/` 要重启才生效。**但用户要的不是"刷新能重读数据库"**——他要的是**只手摸 `session-trash/`（文件那边）就好**（"如果动文件需要动两处，那很麻烦了，尤其是后者还是数据库"）。

**换代后的机制（原选项"刷新时 close+open 域"作废）**：**每次读清单 = 对账 + 读**——`GET /list` 的正文变成 `reconcileTrash()`（`src/trash/reconcile.ts`）：以 `session-trash/` 里的目录为准，把清单修回一致。于是"重开域"没有存在意义了（它服务的"手工编辑数据库"正是要避免的方向）；挂载、刷新、别处动过后的自动重读全走 `list`（**客户端启动探测 2026-10-17 起改走 `GET /ping`**，见现状稿第十二批）⇒ **改完目录不做任何事，下一次读就对**。零线格式改动、浏览器半零改动。

**五条口径**（都在 `reconcile.ts` 的头注里）：

| # | 口径 | 理由 |
|---|---|---|
| ① | 每次 `list` 对账；零漂移零写入（快路直接返回） | 代价 = 每次读多一次目录枚举（本机 124 条，毫秒级） |
| ② | **回收站根不在 ⇒ 整套跳过、一个字节都不动** | 那不是"回收站空了"，是"这块地不在原处"——照常对账会把全部行的元数据一次判没 |
| ③ | 重建行只写**文件里真有的事实**：`id`=目录名、`sessionId`/`cwd` 读日志 header、`projectDir` 由 cwd 反推、`deletedAt` 从目录名时间戳解、`sizeBytes` 现场量；**文件侧没有副本的三件按缺省落**：`workspaceId:''`（恢复落「未分组」）、`wasArchived:false`（按可见还原）、`title:''`（详情有日志标题兜底） | 这两格只住在清单行里，是重建的固有代价 |
| ④ | 认不出/读不出的目录（坏名字、没日志、header 读不出、尺寸量不出）**不动、不列**，各跳过各的 | 那是"外人放进来的东西"，不是用户动作失败；半截行（比如尺寸量不出还硬造）比"不列"更坏——恢复会照它把目录搬去错地方 |
| ⑤ | **幂等**：再跑零写入；崩在任何一步，下一次读接着修 | 对账是修复路径，任何中断都不留坏状态 |

**`projectDir` 反推链（承重前提，已验）**：header 的 `cwd` → 宿主同名算法 `projectKey`（逐字镜像本来就在 `src/ports/host-port.ts`，13 行）。验证两层：① 现拉 `@deepseek-ai/dsh-session-persistence-jsonl@0.2.0-rc.2` 与 npx 缓存里的 0.1.0-rc.7 对照，`projectKey` 逐字相同；② 拿真机 `~/.dsh/sessions/` 下 6 个项目的会话日志 header 反算，**6/6 复现目录名**（含中文 `~XXXX` 与分隔符折叠：`C:\Users\…\Desktop\文件\专利技术交底书` → `--…-Desktop-~6587~4EF6-~4E13~5229…--`）。

**与写动词的串行化**（`src/api/dispatch.ts` 的到达序链）：对账与删除/恢复/彻底删除都是"读清单 + 动文件 + 写清单"的多步，交错跑会互相踩——删除刚把目录搬进回收站、行还没写上时，对账抢先把这行按目录"重建"出来，再被真实行覆盖成降级元数据。链把 `list` 与三个写动词按到达序排队（`detail` 是纯读、不占链）；代价只是排队（单进程单用户，毫秒级）。

**台架读数（临时 `DSH_HOME` + web 模板 + `plugin add link:`，宿主 `0.2.0-rc.2`，真 Chrome）**：预置两处漂移（只有目录没有行 / 只有行没有目录）+ 回收站根里一个杂散文件。① 打开面板（首读即对账）：幽灵目录**长出了行**（组头 `C-develop-bench-ghost` 由 header 的 cwd 反推、`删除于 1小时前 · 104B` 现场量）、孤儿行**被摘**、`README.txt` 没被列；② 运行中把目录改名搬走 → 点面板刷新 → 行**当场消失**（空态），不用重启；③ 改回来 → 点刷新 → 行**当场回来**；④ 对重建出来的行走「彻底删除… → 彻底删除」真通路：目录与行都清掉，杂散文件未动；⑤ 控制台零条 error/warn。**"手工动回收站只动 `session-trash/`"这条至此在活宿主上闭环。**

**真机门交用户**：他是在真机上发现"刷新不动"的，改完后的目视（以及他后续手工整理回收站的习惯用法）由他跑；判据 = 上面 ①–③ 三条在他的桌面版上照做一遍。用例账与构建读数住现状稿 §8。

## 10. 清单行上的「含 N 个子会话」（2026-10-16 第八批：五格阶梯的第一格；级联在 §11）

> **2026-10-19 评审修正批注**：本节与 §11/§12 里的 `strandedSubagents` 来源、释放量与 purge 目标已随第十七批扩展——来源改为 `subagentMembersBatch` 并新增 `strandedBytes`；计数只数目录真在盘上的成员；`purge` 目标还纳入盘上后代；单条释放量还含 `strandedBytes`。现行口径以 `docs/design/2026-09-30-session-delete-design.md` 的第十七批与评审修正批为准。

**为什么这一栏非有不可（本机一次性探针，跑完即删）**：header 上的 `origin` **只有 `subagent` 一个取值**（缺席 = 普通会话；`dsh-api-session-controller/lib/typert.host.js:2157`，代次 `0.2.0-rc.2`）。宿主的 `list()` **不筛**孩子，摘要里带着 `parentSessionId` / `origin`，但**客户端整排藏掉**——`dsh-client-ui-workspace/lib/client.js:358` 逐字 `if (session.origin === "subagent") return false;`，工作区成员与「未分组」那一桶（:430 / :436）过的是同一个过滤器 ⇒ 孩子既不显形，也**永远不会**变成幽灵行。于是"删了父还剩多少"这件事在界面上一个字都看不见。

本机存量：**549 个可读会话目录里 541 个是 `subagent`**；回收站 127 条全是父会话，其中 **41 条的孩子还在盘上，共 320 个目录 / 74.6 MB**（最大一条就占 98 个目录 / 22.2 MB）；另有 **36 个活着的父合法持有 221 个目录 / 57.8 MB**——那批不该动，画在图里也是要说清这件事。宿主帮了一半：`ArchivedSessionGate` 顺 `header.parentSession` 拦，父一归档孩子就跑不动（`dsh-api-session-controller/lib/types/archived-session-gate.js:35-51`），**但字节照样占着**。

**这一格只做"说出来"**：删除语义一个字没动。

**取数走官方面，不自扫盘**：`ctx.sessionQuery.filterSessions([{ kind:'parent', values }])`，宿主判据逐字是 `filter.values.includes(record.header.parentSession ?? null)`（`dsh-session-query/lib/index.js` 的 `sessionPredicate`；`filterSessions` 的 JSDoc 原文 "matching cloned records in deterministic newest-first order"，且它**不是**按连接鉴权裁剪的那一支）。`sessionQuery` 按**可选服务**读（`ctx.get`，不进 `inject`——同 `sessionProjectionCache` 的处理）。归堆必须**两边都剥 `session-` 前缀**：本机实测父自己的 header id 带前缀（`session-ac07f2bb-…`）、它的孩子写的 `parentSession` 也带，而 v3 那一代的 id 不带 ⇒ 同一个父有两种写法；于是问的时候把一个 id 的两种形状都塞进 `values`，回来按剥前缀后的形状加总，键按**调用方给的那个写法**交回去。

**两道口径，都不是口味**：① **计数不落清册**，只加在 `GET /list` 这一次回信上——清册该记"文件里真有的事实"，而"还剩几个孩子"是随盘上随时变的数，写进去就等于让 §9 那条对账下次拿一个目录里查无此物的数来说谎。② **报不出就不说**：服务没挂、或这一条确实没孩子 ⇒ 界面上半句都不出现，不许拿「含 0 个」冒充「不知道」。取数失败**照抛**（响亮失败那条），不端一份"少了这栏的清单"当没事发生。

**落点**：`src/ports/host-port.ts` 的 `subagentCounts`（端口第十三员）→ `src/api/dispatch.ts` 的 `list` 分支（对账之后、回信之前）→ `src/client/remote.ts` 的 `subagentCount?` → `src/client/trash-panel.tsx` 那一行的第三段（`copy.ts` 的 `trash.row.subagents`，zh / en 同时加）。没有新控件、没有新层级。

## 11. 级联：删父会话即把它在盘上的孩子一起带走（2026-10-16 第九批，第二格）

§10 那一格只是把 320 个目录 / 74.6 MB 说出来。这一格把它们**跟着父一起进回收站**：删除、恢复、彻底删除都按组走，且仍可恢复。

**孩子的身份与目录从哪来（全官方面）**：`HostPort.subagentMembers(sessionId)`（端口第十四员）走 `ctx.sessionQuery.filterSessions([{kind:'parent', values}])`——宿主判据逐字 `values.includes(record.header.parentSession ?? null)`，交回的是**带 header 的记录克隆**；孩子的 `sessionId` 取 `header.id`，项目目录由 `header.cwd` 走**同一个** `projectKey`（与 `projectDirOf` 同一根算法，不另起一套）。`header.id` 缺席的孩子**跳过**——不拿目录名冒充身份，冒充了就会把一个来路不明的目录搬进回收站。问的时候把一个 id 的两种写法（`x` 与 `session-x`）都塞进 `values`，因为本机实测同一个父有两种写法（v3 代不带前缀、v4 带）。`sessionQuery` 是**可选服务**（`ctx.get` 读，不进 `inject`）；它没挂就回空组 ⇒ 删除照旧只管父，不因此失败。

**三段顺序，都是承重的**（`src/verbs/delete-session.ts`）：
1. **先点组、先验活体，一个字节都不写**。父与每个孩子逐个查 `isLive`，任一个在跑就**整组拒绝**（`sessiondelete/live`）——不替用户终止正在跑的活，也绝不允许"父已进回收站、孩子因为在跑搬不动"那种半套。
2. **逐个搬**，每个成员内部沿用原来那五触点与就地回滚（归档 → 摘账本 → 搬目录 → 写清册 → 摘内存 + 通告）。孩子先归档再摘账本那条理由一模一样：`listSessions()` 是"持久化 ∪ 活体"的并集，只搬文件会让孩子掉进「未分组」。
3. **组级回滚**：某个成员搬不动时，把**已经搬进去的**按相反顺序退回原处（行回到清册、目录搬回 `sessions/`、账本挂回、可见性还原、通告"回来了"），失败照抛。

**清册只多一件事实**：`TrashEntry.parentEntryId?`（`src/trash/entry.ts`）。孩子那一行记父那一行的 `id`。**目录布局一点没动**——每个孩子仍是 `session-trash/<它自己的条目 id>` 这样一格，与存量那 127 条同形，所以 §9 的对账不需要新概念。文件侧没有 `parentEntryId` 的副本，所以清册被清后由目录重建出来的行**不带分组**、各占一行；那是"分组信息随清册一起没了"的如实结果，不假装知道（与 `workspaceId`/`wasArchived`/`title` 同一类降级，§9 第③条）。

**清单的装配**（`src/api/dispatch.ts` 的 `assembleTrashRows`）：只列父行，孩子折进去，并另加只读的派生值交出去——这一批加的是 `subagentCount` / `subagentBytes`（组内一起进来的，来源是清册）与 `strandedSubagents`（**盘上还留着没被带走的**；2026-10-19 评审修正批起来源改为 `subagentMembersBatch`、并新增 `strandedBytes`，且只数目录真在盘上的成员）。**派生值的总数不钉在这里**（后来者见现状稿第十四批；钉一个数就是下一条会漂的陈述）。三道防线：
- **两个数不许互相冒充**：界面上分别说「含 N 个子会话」和「盘上还剩 M 个子会话」。级联落地前删的那些存量只会亮后者——说成"含"就是假话，用户会以为恢复能把它捞回来。
- **隐形防护**：折进父行的前提是**父行在**。父行不见了（手工摘的、清册半损的），孩子自己站出来占一行——否则那一条既看不见也清不掉，正是本仓一直在躲的"点不到的行"。
- **合计要算得上孩子**：`sizeBytes` 仍是那一条会话自己的（详情里对得上），头部合计另加 `subagentBytes` 与 `strandedBytes`。只加父那一格就会少报。
- 三个字段**都不落清册**（清册该记文件里真有的事实，而"还剩几个"随盘上随时变）。

**恢复与彻底删除按组走**：`restoreSession(父 id)` 先**预检整组**（每个成员的回收站目录与原项目目录都得在）再逐个搬回，所以"父回来了、孩子因为项目目录没了回不去"这种半组留在外面的世界不会发生；中途失败把已完成兄弟一起退回。`purgeTrash(父 id)` 的目标集是"父 + 指向它的孩子 + 盘上后代"（2026-10-19 评审修正批扩展），`removed` 报的是整组条数。按孩子 id 单独走那两个动词（清单不列孩子，只有手工/降级路径会走到）就只动它自己。

**真机门（交用户，桌面版 `0.2.0-rc.2`；①–⑥ 全过这格才算落）**：① 挑一条**盘上有孩子**的会话删除 → 回收站只多**一行**，那行说「含 N 个子会话」，N 与 `~/.dsh/sessions` 下按 `parentSession` 数出来的一致；② `~/.dsh/session-trash/` 下真的多出 N+1 个目录（父与每个孩子各一格），`~/.dsh/sessions` 里那 N 个孩子的目录同时消失；③ 恢复那一行 → N+1 个目录一起回到 `sessions/` 原来的项目目录下，回收站那行消失；④ 对一条**有孩子**的用「彻底删除…」→ 整组目录与行都不剩，头部合计相应减少；⑤ 级联落地**之前**删的那些老行仍亮「盘上还剩 M 个子会话」，且不说成"含"；⑥ 控制台零 error/warn。**注**：`subagentMembers` 的真实绑定单测只钉了接线形状。原本挂在这一趟的两条已在 2026-10-16 **静态坐实**，不必等真机：① 服务与包都在（`super(ctx, "sessionQuery")` 在 `dsh-session-query/lib/index.js:1046`，桌面 `0.2.0-rc.2` 的 `dsh` 直接依赖该包）；② `header.id` **就是**目录名那一段——本机 554 个会话目录 **554/554** 逐字相同，回收站条目名那一段 **130/130** 相同（只读探针，跑完即删）。所以级联那条「拿 `header.id` 拼路径」是准的；这一趟剩下的是①–⑥那六条行为读数。

用例账：本格新增 **19 条**（`assembly` 四：`subagentMembers`；`delete-session` 四：整组搬入 / 孩子目录缺席跳过 / 孩子在跑整组拒 / 组级回滚；`restore-session` 三：整组回 / 预检拦半组 / 孩子单回；`purge-trash` 二：整组清 / 孩子单清；`api` 净三：只列父行、"还剩"不出现、隐形防护（原「计数不落清册」那条改写进这批）；`trash-panel` 三：「还剩」不冒充「含」、两句并存、合计含孩子字节），全量 **342 通过**；`tsc --noEmit` 干净；`npm run build` 过纯度门。

**构建读数**：住现状稿 §8（第八与第九批同一次提交 `45536e2`，两批共用那一趟产物）。issue #5 之所以单开一张票，就是因为这两批当时只记了用例数、没记产物读数——现在补上了。

## 12. 五个 issue 的收口批：组是「全部后代」，两个数各住各家（2026-10-16 第十批）

§11 落地后的两轴评审开出五张票（issues #1–#5）：四条动代码、一条只动文档。判据与代价逐条如下，被否决的替代跟在每条后面。

**① 组 = 传递闭包，不是"直接孩子"（#1）**。级联当时只问一层 `kind:'parent'` ⇒ 孙代留在 `~/.dsh/sessions/`：既搬不进回收站，也不进「盘上还剩 M 个子会话」那个数。而宿主客户端对所有 `origin:"subagent"` 一律藏行（§10 那条 `sessionVisible`）⇒ **深度 ≥2 上"删了父还剩多少本来看不见"原样存在**，只数一层就是把那件事说成没有。本机存量（2026-10-16 只读探针，跑完即删）：**554 个会话目录里 20 个是「孩子的孩子」**（`parentSession` 指向一个自己也有父的会话），而那 20 个的爷爷**目前一个都不在盘上** ⇒ 今天没有可触发的链，这张票是"现在修"不是"已经坏了"。
- **问法只有一条**：`kind:'parent'` **一次问一层**，问到那一层没有新记录为止。官方的 `traceSession(id)` 直接交出传递闭包（api-catalog 逐字 "Trace known ancestry and descendants"），但它在**父已经进回收站**时认不出目标（`SESSION_QUERY_SESSION_NOT_FOUND`）——我们要的那批恰恰是"父不在宿主列表里之后还留在盘上的那些"，所以够不到。**被否的替代**：① 只走一层 + 把这条边界写进文档（写就是承认界面上那个数会说谎）；② 自扫 `~/.dsh/sessions` 读 header 建全图（能算对，但 §10 那条"取数走官方面"的口径就废了，且每次读清单多一遍全盘扫）。
- **落点**：`descendantsByParent`（一张 `父（bare）→ 后代` 的索引，逐层问出来）+ `subtreeOf`（沿这张索引往下收），两个端口成员共用；`src/verbs/delete-session.ts` **一行没改**——它拿的是 `subagentMembers`，端口交回全部后代，那三段（整组准入 / 逐个搬 / 组级回滚）本来就不关心深度。
- **清册里的组仍是平的**：每个跟着进来的后代都记**根**那一行的 id（不是自己爸那一行）。所以 §11 那句「目录布局一点没动」继续成立，`assembleTrashRows` 也继续只看一层——深度这件事只住在"盘点人"那一侧。
- **代价的口径**：宿主调用次数由**层数**决定，与清单行数无关——`subagentCounts` 把所有可见行合成一趟 BFS（本机最深三层 ⇒ 三次 `filterSessions`），不是每行各扫一遍库（用例钉住了这条）。
- **环**：`seen` 连着根一起记 ⇒ 数据里真出现环（手工改过日志 / 宿主 bug）的结果是"少数一条"，不是把清单读挂死。
- 界面两句一个字没改，但**两个数现在同按闭包算**：「含 N 个子会话」= 跟着进来的，「盘上还剩 M 个子会话」= 没带走的，来源仍各是各的（清册 / `sessionQuery`）。

**② 「折进谁」与「谁露面」合成一条判据（#4）**。旧写法两条不同源：「露面」看 `parentIds`（只由 `parentEntryId === undefined` 的行构成），「折进去」另起一次 `rows.filter(k => k.parentEntryId === row.id)`。于是"父行自己也是孩子"那种清册（A 的父不在、A 的孩子在）会让那条孩子行**既自己占一行、又被折进 A 那一格** ⇒ 头部合计把它的字节数两遍。今天写不出那种清册（`deleteSession` 只给跟着根进来的后代写 `parentEntryId`，根行自己不记父），所以是潜在项——但它是这套折行语义里唯一一处自己跟自己不一致的地方，留着就是下一次改动踩上去的坑。
- **改成一条**：**接得住孩子的只有根行**（父行**在**、且父行**自己没有 `parentEntryId`**）。先算一张 `foldedInto`，`visible` 与 `kidsByParent` 都从这张表派生 ⇒ 顺带把每行一次的 `rows.filter` 收成一次遍历。父行不在时孩子照样自己站出来占一行（§11 那条隐形防护一字没动）。
- 用例钉的形状：mid（父行不在）+ leaf（它的父是 mid）⇒ 两条都露面、谁都没把对方折进自己那一格。

**③ 彻底删除那一格改说「这次会释放多少」（#2）**。单条「彻底删除…」的确认卡片写的是父自己的 `sizeBytes`，而彻底删除按组走、头部合计早就算上 `subagentBytes`（2026-10-19 评审修正批起还有 `strandedBytes`）⇒ 同一屏两套口径。**裁定取「我即将失去什么」**：那一格改成父 + 折进来的孩子 + 仍留在盘上的后代（`strandedBytes`），并与头部合计**共用同一个数**（`releaseBytes`，由 `api/trash-rows.ts` 的 `toWire` 唯一算出，见第十八批候选 8）——两处各写一遍加法就是下一次漂移的地方。**被否的替代**：只在 §7 落一句"这一格说的是这一行多大"（口径是解释了，但用户拿它估"能腾出多少"仍然错）。清单行里那个 `{size}` **不动**：它挨着「含 N 个子会话」，说的是这条会话自己多大，详情里对得上（§11「合计要算得上孩子」那条的分工照旧）。

**④ 删除确认框在点之前就说清有多少跟着走（#3）**。症状：本机最大一条父会话留了 **98 个**后代（§10 存量），用户点完才发现侧栏少了一整片，而那些行宿主的列表里本来就不显示 ⇒ "少了什么"不可自证；撤销提示停留 6 秒，所以不是不可逆，只是**点之前不知道**。
- **要这句话就得在删除前取一次数**，而那个数只能现问宿主：那一刻会话还在盘上，`/list` 里没有它 ⇒ 开**第六个端点** `POST /subagent-count`（体 `{sessionId}`，值就是一个数）。它挂在 `subagentCounts` 上 ⇒ **与级联同一个闭包口径**（同一个数两处说，不能一处一层一处闭包）。错误码一个都不新增：`requireString` / 同源栅栏 / `map-error` 那张表整套复用，同 §3 那条「用 POST 表达一个读」的裁决。**（2026-10-17 第十二批：这一段名已退役——它现在是 `POST /apply` 的 `action:"count"` 一支，纯读、仍不进串行链，口径一个字没改；段名总数现在是六个——2026-10-19 评审修正批又加了 `GET /orphans`。）**
- **它与 `detail` 一样是纯读 ⇒ 不进那条到达序串行链**：一次计数不该被前面一次对账堵在身后（用例钉的正是"链被占住时它照样立刻回"）。

## 13. 批量恢复：多选的另一半（2026-10-17 第十一批）
用户原话：「现在多谢（多选）只能批量删除，我希望也可以批量恢复」＋「批量恢复最好也有确认框，因为恢复的条目太多了，也需要确认。逐条恢复自然不需要确认框。」§7 那条「只批量彻底删除，不批量恢复」由此翻全。

**形状**（三件判据）：
- 页脚在多选态出**两颗**：「恢复 N 条」描边 + 「彻底删除 N 条」实心红——**实心红仍在最末位**（"整页唯一一块实心红"的规矩靠不换位置来守，不是靠只许有一颗）。一条没勾时两颗都置灰，悬停原因同走 Tooltip。
- **批量恢复带确认框、单行恢复仍直接执行**（用户裁定）：框里列出这一批的**每一条**（标题 + 项目名，卡片纵列、最高 280px 自滚），正文一句 `trash.confirm.restore.body` 说清去向（"回到各自的原项目目录，恢复到会话列表里"）。确认键是「恢复」（**不带计数**——与「彻底删除」那对的形状对齐），页脚那颗才是「恢复 N 条」。恢复是加法，正文**不出现**「没有任何副本可以恢复」那句（那批不可逆警告归 purge 的框）。
- **执行与批量彻底删除同构**：串行逐条 `restore(id)`（不新增端点、不碰 Node 半），顺序按**清单从上往下**（不按点击顺序）；失败原文落在它自己那一行、多选态不退，成功的随重读消失（勾选计数跟着降）。**（同日被第十二批改写，本行保留当时的形状）**：那条"每条一次 HTTP、每条内部再读一遍全表"的代价在真机上被用户的"一百多条很慢"量了出来 ⇒ 现在整批是**一次 `POST /apply`**（`{action:"restore", ids:[…]}`），清册只读一次、宿主会话表只预取一次、通告一次批量发（发的是**整组**的 sessionId，孩子不漏）；"失败落回自己那一行"改由接口保证，不再由调用方拼。判据与账见现状稿第十二批。

**一处连带修正**：页脚说明句不再分「清理/多选」两版——多选态现在能删也能恢复，「选中的 N 条彻底删除后不可恢复」在准备批量恢复时是假话。两版合成一版（`trash.footer.note`：回收站在哪 + 不自动过期），动作专属的警告归各自的确认框；`trash.footer.noteBulk` 键（zh+en）随之删除。`trash.select.needOne` 从「先勾选要彻底删除的会话」改成「先勾选要处理的会话」（两颗按钮共用一个提示）。

**用例账**：`trash-panel` 新增 **3 条**（没勾时置灰且不弹框、确认框列出条目并按清单顺序逐条 restore 且成功后不留行、部分失败原文落回自己行）+ `depsOf` 替身补 `restore` 覆写。**踩坑记一笔**：确认框那颗「恢复」与页脚那颗「恢复 2 条」**不同名**（同「彻底删除」那对的形状），第一版用例按同名去找、点了两次页脚那颗，表现是"只恢复了一条就卡住"——定位靠框内按钮 dump。全量 **361 通过**；`tsc --noEmit` 0；`tsdown` 0（读数见现状稿 §8）。

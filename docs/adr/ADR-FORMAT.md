# ADR 规范

> 以 domain-modeling 技能的 ADR-FORMAT.md 为底、按本仓既有 ADR 的复杂度校准；与 `AGENTS.md` 的硬门冲突时以 `AGENTS.md` 为准。

## 文件与编号

- 放在 `docs/adr/`，命名 `NNNN-slug.md`（顺序编号 + 短横线小写 slug）。
- 编号扫现有最大号 +1，不复用、不跳号；只追加、别重排。

## 什么时候写

三条判据同时成立才写：

1. **难以回退**：事后改变主意的代价足够大。
2. **无上下文会令人惊讶**：未来的读者看代码会问「为什么当初要这么做？」
3. **真实权衡的产物**：确实存在别的可选方案，而你基于具体理由选了这一个。

容易回退的不写；不令人惊讶的不写；没有真实替代方案的不写。够格的典型是架构形状、边界与归属、刻意的技术选型、拦着下一个人去「修好」的刻意偏离。

## 结构

每篇至少要有：决策式标题（读完标题即知结论）、`**状态**`（已接受 / superseded + 日期）、`**相关**`（相关 ADR 与代码位置）。导语 1~3 句说清背景一句 + 决定一句 + 理由半句；只有标题 + 导语也是合格 ADR。

决策重一分，多加一件：

| 章节 | 什么时候加 |
| --- | --- |
| `## 背景` | 「为什么」一句话装不下：多股作用力、要澄清的误报、历史包袱。讲当时为什么变，用过去时。 |
| `## 决定` | 决定多于一件互相牵连的事，或单条决定需要分条展开约束。编号条目，每条自带理由。 |
| `## 边界` | 明确不做什么、哪些语义仍归别的家，防止下一步改错地方。 |
| `## 后果` | 改动横跨多模块/多文件，读者需要知道波及面；用现在时描述落地后的现状。 |
| `## 被否掉的替代` | 拒绝本身需要论证、不记会被重提时。逐条给理由。 |

专项章节按需命名（例如「行为差异」「客户端主视图」）；同一篇内章节名保持一致。

## 翻案怎么落字

- 推翻**整篇**：在该篇头部把状态改成 `superseded`，指向接手的篇号；正文保留，别删历史。
- 只翻**其中一条**：不动正文，就地补一条带日期的「就地订正」括注，说清现在谁说了算。
- 决定/边界/后果用现在时描述**落地后的现状**；背景保留当时的历史。代码与测试是最终真相，文档冲突时改文档。

## 写作纪律

- **引用历史写日期，别写批次号**：读者手上没有能查的批次坐标；有 commit 就带上，要指裁决就指 ADR 篇号。
- **ADR 不写现状地图**：系统分成哪几块、某条语义归谁，住 `docs/architecture.md`；这里只回答「当初为什么这么定、被否掉的是什么」。
- **不抄读数与计数**：构建产物大小、文件数、测试数这类会腐烂的数字不写进 ADR；要证据就指测试或代码。
- **点名仓内路径必须真实存在**：`tests/docs.test.ts` 的文档门会扫；改名或删除时同步改这里，或改指还活着的家。
- **不层层打补丁**：同一篇内不要堆积一串「后来又改回……」；翻案按上面的口径落字，或把整篇重写后标 superseded。

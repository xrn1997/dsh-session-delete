# ADR-0072 — 移入回收站统一即执行，不弹确认框

Status: accepted

会话行菜单、批量按钮、归档档与拖放都统一为「移入回收站」即执行；成功发撤销横幅，失败原文落到通知或对应行。不可恢复的彻底删除、清空回收站与孤儿清理仍保留二次确认。本决定取代 ADR-0071 的「行菜单确认与拖拽即删并存」。

## 决定

1. **所有移入回收站入口同一口径**：菜单、批量、归档与拖放都直接走既有移入写入座位，不再经过确认框。菜单文案改为「移入回收站」，让入口本身说明去向；「删除」不再作这个动作的名字——那两个字只属于永久删除，词表住 `CONTEXT.md`。
2. **移入回收站不为提示子会话数额外取数**：宿主列表本来就隐藏后代，旧确认框的 `count` 只能补一句说明，不能构成防误操作屏障；批量「查看已选」仍可显示已选根行的计数，但那不是执行门槛。
3. **结果反馈仍完整保留**：成功走撤销横幅与可恢复回收站；单条失败与全失败进裸失败提示立即可见（不被上一条成功横幅挡住），批量部分失败随当前撤销横幅同屏展示并收缩勾选到失败项，归档失败按行落原文。在飞的 `/progress` 进度行不在此列——它住在确认框里，随框一起消失（见「代价」）。

## 边界

- 彻底删除、清空回收站、无主子会话清理不可恢复，确认框与危险层级不变。
- 恢复的确认面不动：批量恢复的确认框照旧，单条恢复本来就是即执行；移入回收站 / 恢复不碰归档的领域语义不变。
- 撤销横幅的停留时间不是安全边界；回收站不自动过期，用户随时可手动恢复。

## 被否方案

- **保留移入回收站确认，理由是彻底删除已经有确认**：两层确认防的是不同后果；不可恢复动作的确认不能替代可恢复动作的信息设计，反而让同一动作在点选与拖拽路径上不一致。
- **只去掉单条确认，批量仍确认**：批量拖放已经即执行，继续保留按钮确认会留下新的路径差异；批量清单也已提供操作前的复核面。
- **把子会话数量换到另一个轻量弹层**：仍是为可恢复动作增加一步，没有改变用户要承担的交互成本。

## 代价

删前不再显示目标卡与后代数量，用户要依靠明确的「移入回收站」文案、撤销横幅和回收站恢复来纠错。确认框一族的 `/progress` 进度行也随框一起消失：移入回收站不再有 k/N 进度行（写入遥测照旧记录，只是没有界面认领；恢复、彻底删除与清空的进度面不动），点击到完成之间只有批量按钮的忙碌转圈与置灰挡重按。接受这些代价，是因为移入回收站本身可恢复，而旧确认框在计数读不到时本来也不会禁用操作。

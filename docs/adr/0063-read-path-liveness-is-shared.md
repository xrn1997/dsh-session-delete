# 失效是事实、读是动作：三个读路径共用一条重读生命周期

Status: accepted

归档清单、归档详情、回收站清单三处各自用 effect 订阅修订号并重读，导致「不可见的档也读」与「修订风暴里按事件数重读」；把节奏收进 `useGatedRefresh` 一条生命周期，消费者只保留各自的数据语义（latest-wins、失败上屏、账本作废）。之所以必须共用：档位门、合并窗与单飞是同一组判据，分写三份就会各自漂移。

## 背景

修改前，三处各写一条「修订变了就重读」：

- 归档详情 reader 没有档位门（它只在有 subject 时才有读需求，而原先的失效 effect 不认这一点）：归档档在回收站档后面时，每次宿主归档集变化仍去读一整本 `readSession`，读到的结果连屏幕都上不了。
- 回收站控制器同样没有门：用户停在归档档做动作时，回收站清单也在后台重读。
- 三处都没有单飞与合并：一次批量写后通告跨多个 tick 到达，每来一次修订就发一次读；归档详情那条还是整本读，作废的在飞票按事件数白打往返。
- 归档详情那条修订 effect 每次 `clearAll()` 再 `ensure()`，于是「在飞期间的新修订」会把在飞读数丢掉重发，风暴里请求数跟事件数走。

根因不是某一个 effect 写错，而是这三条判据（档位门 / 合并 / 单飞）没有单一的家：每处都要自己再写一遍，写漏一条就退化成上面某个现象。

## 决定

1. **一条生命周期负责节奏，消费者只负责内容。** `src/client/use-gated-refresh.ts` 的 `useGatedRefresh` 是「修订到达 → 作废 → 按需排读」的唯一实现。它管：修订到达时同步置脏、按消费者策略跑**便宜**的 `onInvalidate`、档位门、合并窗、单飞与追补、卸载与晚到结算的边界。`latest-wins`、失败上屏、账本与快照语义仍归各消费者自己的 `refresh`/状态机——生命周期不知道读的是什么，也不产生渲染态。
2. **两道门：`active` 与 `demand`。** `active` 是档位在眼前（面板传档位判据），`demand` 是这一档此刻有没有读需求（归档 reader 传 `subject !== null`）。两道门都开才发起读；不活动/无需求时只记 dirty，门开那一拍补读。门在**排读时**与**落地前**各验一次：排队期间关档/丢主体，票作废、dirty 留着，切回时恰好一次。
3. **挂载不是一次修订。** 挂载只记签名，不作废、不置脏。清单类在挂载/激活时读第一趟（`initialDirty`、归档清单的 `refreshOnActivate`）；详情类等主体出现后由调用方自己的首读逻辑负责。这样 `initialDirty` 才是真选项，而不是「挂载恒脏」的别名。
4. **修订风暴收敛。** 同一窗口内的多次修订合并成一次读：清单类用微任务合批，详情类用 `DEFAULT_REFRESH_COALESCE_MS`（120ms）的 trailing 窗——整本详情读比清单读贵，值得多等一个不可感的窗口。在飞期间的新修订只置脏；结算后至多一轮追补，生命周期自己的 refresh 绝不并发第二条（点选/意图预取这类带外读可与在途 refresh 重叠，旧票换代丢弃——有界，且是本决定之前就有的既有行为）。强制激活（`refreshOnActivate`）同样吃两道门与单飞。
5. **贵的作废放在 refresh 里，不等同于「修订当场清账本」。** 归档详情 reader 的 `clearAll` 会连同在飞登记一起清掉，而通用读者在「主体在场、账本为空、没在读」时会由兜底 effect 立刻补读——修订当场作废等于给每一发修订开一条绕过窗口与单飞的读。归档 reader 因此把 `clearAll` 放进 refresh：合并窗到点先作废、同一拍 `ensure`，兜底那一拍看到的已经是「在读」；代价是旧归档态最多多留一个窗口（120ms），但整本读只发一次。
6. **不轮询、不用 AbortController。** 定时器只有合并窗这一颗，卸载即清；作废在飞读数靠身份票（换代），不试图中断已经发出的通道请求——请求本身不可 abort，省的是重发而不是在途。

## 边界

- `latest-wins` / 失败态 / 重试动作 / 清册快照 / 选择面仍归各消费者；生命周期只发 `refresh`、只收 `onInvalidate`。
- 归档详情 reader 的「档位不活动 = 无读需求」由控制器交 `subject: null` 表达（reader 的既有 seam），生命周期不认识档位。
- 归档 reader 的整本账本作废由它自己在 refresh 里做（见决定第 5 条）：`onInvalidate` 只对便宜的现场作废负责；生命周期不替消费者决定「什么时候清账本」。
- 回收站面板的首次挂载读仍由同一个控制器发（`initialDirty: true`），面板只把档位活动面派生一次传下来。
- 失效粒度仍是整条修订号：宿主归档集变化即作废整本归档详情账本（ADR-0060 第 4 条），本决定不改失效粒度。
- 两个档位的状态仍互不相通；共用的是节奏，不是状态。

## 被否方案

- **三处各修各的 effect**：同一组判据三份实现，风暴与档位门的漂移只是时间问题；这次修的正是第三份（详情 reader）写漏。
- **用轮询兜底**：ADR-0036 的「订阅不轮询」仍成立；轮询还会制造空读，和「不可见不读」相反。
- **给生命周期加 AbortController**：宿主通道是 exact Fetch 路由，abort 只能省客户端等待，不能消服务端已发生的读；换票 + 单飞已把重发压到有界，加 abort 只增复杂度。
- **精确失效（A1 携带 changed ids，只重读受影响主体）**：能进一步减少整本重读，但要改 `archive-store` 的修订台契约与 A1 观察面的形状；先把节奏收口，粒度留作后续独立决定。
- **把合并窗做成用户可调项**：内部实现细节不外露；120ms 是「短到不可感、长到能收一批写后通告」的折中，需要时改常量。
- **强制激活无视 demand 门**：会给未来消费者留一个「无需求也读」的后门；强制的是「激活时必读」，不是「没有主体也读」。
